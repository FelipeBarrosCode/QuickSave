# Native OS browser handoff

The service's `crates/quicksave-service/src/oauth.rs` now calls Win32
`ShellExecuteExW` directly after the native gateway's consent and this crate's
pure parsed/canonical HTTPS origin validation. No PowerShell, cmd, rundll32,
PATH, environment-based executable selection or account probe is used.

`validate_authorization_browser_url(&str) -> anyhow::Result<()>` allows exactly
the Google, Microsoft, Dropbox and Box authorization origins, with no userinfo,
non-default port, fragment, backslash, controls or noncanonical spelling. Browser
URLs are generated by the native OAuth flow, not supplied as JS authority.
The service explicitly selects Box's confidential entry point when Box was the
native-approved kind; normal `authorize` still does not downgrade PKCE.

The Windows handoff uses a dedicated COM STA thread, the `open` verb, null
parameters/class/ID-list, no environment substitution, no zone-check bypass and
no wait for browser exit/input idle. It requires both the real API BOOL success
and `hInstApp > 32`; native failures are not treated as success. Any returned
process handle is checked/closed, never killed. A null process is documented and
valid when the OS reuses the user's existing browser.

The caller waits at most three seconds. Extensible Shell/COM code cannot safely
be terminated: a timed-out OS call may outlive the caller and may launch late.
That is an **unknown handoff**, not OAuth success; the OAuth flow closes its
listener on opener failure. A process-wide one-job gate prevents unbounded
accumulation of stuck native threads. No retry spawns a second job while the
first is pending. The UTF-16 authorization URL remains zeroizing native memory.

macOS's fixed `/usr/bin/open` + pinned SafeRoot checks and Linux's existing
trusted `/usr/bin/xdg-open` checks/launch restrictions are preserved.
Feature-disabled builds reject browser handoff before any OS call.

Pure origin/status tests and Windows-gated ABI/flag-construction tests never call
ShellExecuteExW or launch an ambient browser. No Cargo/test execution or native
Windows packaging/browser/account acceptance was performed by this agent.

References reviewed November 17, 2026:
[ShellExecuteExW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shellexecuteexw),
[SHELLEXECUTEINFOW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shellexecuteinfow),
[CoInitializeEx](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-coinitializeex).
They explicitly distinguish accepted OS handoff from authentication and document
that Shell calls can block, URI launches may return no process, and `NOASYNC` is
not a reliable URI timeout mechanism. No fabricated deadline guarantee is made
for the uncancellable OS extension itself.

For the parent's reauthorization/export responses, return only static receipts
such as `{reauthorized:true,providerId,status:"connecting"}` and the state export
API's existing sanitized receipt. Never serialize `NativeOAuthProfile`, expected
CAS generation, tokens/client secret, raw provider/OS error details, repository
key bytes, native destination proofs, or private recovery-file paths into IPC.
